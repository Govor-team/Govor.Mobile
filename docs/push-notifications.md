# Push-уведомления Govor.Mobile

Клиент использует Plugin.FirebasePushNotifications 4.0.23-pre и серверный контракт `/api/pushes/token`.

## Регистрация и выход

После восстановления сессии и проверки сети приложение запрашивает разрешение уведомлений и регистрирует FCM token через авторизованный `POST /api/pushes/token/register`. Тело содержит только `token` и `platform` (`Android`/`iOS`); ответ 204 не требует JSON. Ограничения 512/50 символов проверяются до HTTP-запроса.

Успешная регистрация кэшируется в памяти по userId, sid и FCM token. Новый sid, другой аккаунт, обновление FCM token и новый запуск приложения приводят к регистрации. Неуспешные попытки не кэшируются. Временные ошибки повторяются через 2, 4, 8…60 секунд; восстановление сети и возврат приложения также запускают проверку. Цикл прекращается при выходе и отсутствии разрешения уведомлений.

`IPushNotificationService.UnregisterAsync()` вызывает авторизованный `DELETE /api/pushes/token`, затем снимает регистрацию FCM и очищает очередь событий SDK. При обычном выходе это выполняется до закрытия серверной сессии и удаления JWT. Ошибка отключения не блокирует закрытие сессии. Сервер дополнительно деактивирует токены отозванной сессии. `InitializeAsync()` снова включает регистрацию.

## Обработка сообщений и переход

Поддерживается только `type=chat_message`. Обязательны непустые UUID chatId/messageId/senderId и строковое логическое isGroup. Повреждённые и неподдерживаемые payload игнорируются.

Подписка на события выполняется при создании сервиса, до восстановления авторизации. PersistentQueueFactory сохраняет события SDK между запусками. Нажатие ждёт готовности MainShell и затем открывает личный/групповой чат с messageId; страница синхронизирует сообщения, при необходимости загружает историю и прокручивает к группе, содержащей нужное сообщение. При удалённом/недоступном сообщении остаётся обычный экран чата. При выходе ожидающие переходы удаляются; переходы, связанные с другим аккаунтом, отбрасываются.

Получение и открытие имеют отдельные истории последних 256 messageId в Preferences для каждого аккаунта. Повторное событие получения не мешает первому открытию. История переживает перезапуск, её повреждение восстанавливается автоматически. Уведомление не добавляет сообщение в локальную БД и не подтверждает прочтение: это делает существующий экран чата только для видимых сообщений.

Приложение не создаёт второе локальное уведомление поверх Firebase. Дедупликация обработчиков не гарантирует подавление повторного баннера, уже показанного ОС в фоне. Серверные tag/thread-id объединяют уведомления чата, но не заменяют дедупликацию.

## Настройка платформ

Android:

- Firebase-клиент: `Govor.Mobile/Platforms/Android/google-services.json` для ApplicationId `com.nascode.govor.mobile`.
- Канал `chat_messages` создаётся SDK при запуске, имеет высокий приоритет и выбран каналом по умолчанию. Разрешение POST_NOTIFICATIONS объявлено в манифесте; запрос выполняется через SDK на главном потоке.
- MainActivity использует SingleTask, чтобы нажатие возвращало существующее приложение.

 iOS:

- `Govor.Mobile/Platforms/iOS/GoogleService-Info.plist` включается в bundle при наличии файла.
- `Entitlements.plist` подключает aps-environment. При подписании для распространения проверьте production entitlement в подписанном приложении и соответствующий provisioning profile.
- В Apple Developer включите Push Notifications для App ID; в Firebase загрузите APNs authentication key/certificate для нужного проекта. Эти действия требуют доступа к аккаунтам разработчика.
- Пользователь должен разрешить уведомления в системном диалоге/настройках. Повторного запроса после Denied приложение не делает.

Service account Firebase Admin используется только сервером и в приложение не включается. Сервер должен иметь включённый реальный Firebase provider и применённую миграцию ReliableChatPush. NullPushProvider не доставляет сообщения на устройство.

## Проверка

```powershell
dotnet test Govor.Mobile.Tests/Govor.Mobile.Tests.csproj
dotnet build Govor.Mobile/Govor.Mobile.csproj -f net10.0-android
```

Автотесты покрывают контракт регистрации/удаления, 204, валидацию, повтор после ошибки, одновременные регистрации, смену sid/аккаунта/FCM token, разбор payload и ограниченную постоянную историю дедупликации. Они не проверяют разрешения ОС, фактическую доставку FCM/APNs или UI-переход на устройстве.

На двух физических устройствах проверьте личный чат и группу: приложение открыто, в фоне и завершено; нажатие открывает правильный чат; повтор payload не открывает вторую страницу; смена аккаунта на одном устройстве прекращает уведомления старому аккаунту; выход не затрагивает второе устройство; отказ в разрешении не приводит к повторному диалогу; краткий сбой регистрации восстанавливается без перезапуска. Отдельно проверьте iOS с действующей APNs-конфигурацией и подписью.

Интеграция SDK сверена с [официальным README плагина](https://github.com/thomasgalliker/Plugin.FirebasePushNotifications) и XML-документацией установленной версии пакета. Контракт сервера — документация push-уведомлений Govor, предоставленная для задачи.
